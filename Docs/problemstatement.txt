# Project Objective
Build an offline automated evaluation suite for a Bengaluru Real Estate AI Voice Bot. The pipeline must programmatically score model outputs across three required evaluation dimensions: Feasibility, Edit Correctness, and Grounding & Hallucination.


# Technical Requirements
- The evaluation suite must be completely runnable via CLI (e.g., using `pytest` or a custom Python script `run_evals.py`).
- The suite must execute deterministically against a static "Golden Dataset" (`golden_dataset.json`) of mock conversational scenarios and state JSONs.
- Uses a hybrid evaluation model: Rule-based programmatic assertions combined with LLM-as-a-Judge API calls.


---


# Evaluation Specifications


Please implement the logic for the following three mandatory evaluation modules:


## 1. Feasibility Eval
**Objective:** Verify that recommended properties respect hard user constraints and contain realistic commute claims.
* **Budget & Must-Haves (Rule-Based):**
  - Input: Extracted user constraints (`max_budget`, `bhk`, `amenities`) and recommended property JSON.
  - Logic: Assert that `property.price <= user.max_budget` AND `property.bhk == user.bhk`. Mark test as FAIL if any returned property violates these hard constraints.
* **Commute Claims (LLM-Assisted):**
  - Input: Stated user workplace (e.g., "Koramangala"), recommended property location (e.g., "Whitefield"), and bot response text.
  - Logic: Send prompt to LLM Judge asking: *"Is the bot's commute claim realistic given Bengaluru traffic geography? Return PASS or FAIL with a 1-sentence explanation."*


## 2. Edit Correctness Eval
**Objective:** Ensure multi-turn conversational edits modify ONLY the target parameters without dropping existing context.
* **State Tracking (Rule-Based):**
  - Input: `Previous_State_JSON`, User Edit Utterance (e.g., "Increase budget to 60k"), and `Updated_State_JSON`.
  - Logic: Assert that the targeted key (`budget`) is modified correctly, AND assert that all un-targeted keys (`location`, `bhk`, `amenities`) remain strictly identical. Mark test as FAIL if un-targeted keys are wiped, set to null, or altered.


## 3. Grounding & Hallucination Eval
**Objective:** Prevent the bot from fabricating non-existent listings or neighborhood facts.
* **Listing Validity (Rule-Based):**
  - Input: Bot output JSON containing recommended property IDs.
  - Logic: Assert that each `property_id` exists in the local mock database AND that its `status == "available"`.
* **RAG Source Grounding (LLM-Assisted):**
  - Input: Retrieved RAG text chunks (neighborhood data) and bot response text.
  - Logic: Prompt LLM Judge to check: *"Are all claims about neighborhood amenities fully supported by the provided context chunks? Assign a score from 1 to 5."*
* **Uncertainty Handling (Rule-Based):**
  - Input: Bot response when RAG context is empty.
  - Logic: Assert that the response contains explicit safety/uncertainty keywords (e.g., "I don't have information on", "I am unsure") rather than inventing details.

# Dataset Generation Requirements (`golden_dataset.json`)


Generate a test dataset file named `golden_dataset.json` with 12–15 test cases across 4 specific categories:


1. **Happy Paths (3-4 cases):** Standard searches in popular areas (e.g., HSR Layout, Indiranagar) and straightforward booking requests.
2. **Multi-Turn Edit Edge Cases (3-4 cases):** Users updating budget mid-conversation, changing locality mid-stream, or adding new must-have filters without changing previous constraints.
3. **Adversarial & Out-of-Bounds (3 cases):** Unrealistic budget requests (e.g., 4BHK villa in Indiranagar for 15,000 INR), geographically impossible commute claims, or contradictory filters.
4. **Failure Modes & RAG Edge Cases (3 cases):** Requests where neighborhood RAG data is completely missing, requests for sold/unavailable property IDs, or ambiguous inputs.


### Test Case JSON Schema
Each entry in `golden_dataset.json` must strictly follow this structure:
```json
{
  "test_id": "TC_001",
  "category": "edge_case_edit",
  "description": "User changes BHK requirement from 2 to 3 without dropping budget",
  "input_turns": [],
  "previous_state": {},
  "expected_state": {},
  "expected_behavior": {
    "must_contain_ids": [],
    "uncertainty_expected": false
  }
}
